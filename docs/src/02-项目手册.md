# 柳树沟村 · 数字村落 项目手册

## 一、项目概述

### 1.1 背景

项目要做一个"可漫游、可干预"的三维村庄：既能像看沙盘一样俯瞰全村、点开每一栋房子看档案，也能切到第一人称走进去；时间可以拖、天气要是真的、昼夜要连续。用一句话概括目标——**一个"楚门的世界"式的数字村庄：看起来是布景，但每一阵风、每一场雪都有出处。**

## 四、关键技术

### 4.1 连续太阳位置解算

这是"昼夜不像 PPT"的根本。

早期实现按整点取太阳高度（`Math.floor(hour)`），太阳一小时跳一格；当"一分钟一天"时，每 2.5 秒画面就闪一次。现在改为逐帧解析：

- 太阳赤纬：`dec = 0.409·sin(2π(doy-80.5)/365.24)`
- 时差方程：`eot = 9.87sin2B − 7.53cosB − 1.5sinB`
- 真太阳时正午：`noon = 12 + (120° − 104.04°)/15 − eot/60`
- 时角：`H = (hourOfDay − noon)·15°`
- 高度：`sinAlt = sinφ·sinδ + cosφ·cosδ·cosH`
- 方位：由地平坐标转世界坐标，得到单位方向向量

纬度 φ = 34.4367°、经度 104.0417° 写死在 `climate.js` 顶部。经实测：2025 年 5 月 11 日日出 06:10、日落 19:51，正午太阳高度 68.6°，与气象数据一致。

同一套公式反解日出日落，保证光照与时间显示自洽。

### 4.2 真实气象驱动

岷县 2025 年**晴天只有 7 天、阴天 155 天**，年均云量 68%。这决定了不能用"天气代码"渲染，必须用**连续云量**驱动天空覆盖度：

```
uCoverage = clamp(1.02 − cloudFraction × 0.84, 0.12, 1.0)
```

云层挂在天空球着色器上，按球面坐标采样两层噪声，而不是贴一张平面云图——平面云在低视角会透视拉丝。

气温、湿度、降水、风速都在整点之间线性插值，避免整点跳变。

### 4.3 季节物候着色

季节不能用"换贴图"实现，否则整片山坡会像开关一样突变。做法是给地面、草、叶三套材质注入 `uGreen` 统一变量：

- 绿度曲线：`green = smoothstep(72,132,doy) × (1 − smoothstep(282,328,doy))`
- 地面混合权重 0.46，草 0.86，叶 0.84
- 关键细节：**保持亮度的色调替换**，而不是颜色相乘

```glsl
float lum = dot(diffuseColor.rgb, vec3(0.299,0.587,0.114));
vec3 summer = vec3(0.205,0.375,0.132) * (0.62 + lum*1.18);
diffuseColor.rgb = mix(diffuseColor.rgb, summer, uGreen*0.84);
```

直接用乘法会让绿色过饱和、发荧光。

### 4.4 实例化植被

| 对象 | 数量 | 绘制调用 |
|---|---|---|
| 草叶（基础层） | 15 万 | 1 |
| 草叶（近景层） | 5 万 | 1 |
| 作物 | 约 4.5 万株 | 1 |
| 树干 | 95 | 1 |
| 树枝 | 数百 | 1 |
| 树叶 | 数万 | 1 |
| 家畜 | 16 只 | 32（每只身体 + 头） |

单个草叶是上宽下窄、带弯曲的三角带；叶片是 4×4 细分的曲面（横向微卷、叶尖下垂），并在片元着色器里用背光方向做透射近似，近看不像纸片。

远处植被只有亚像素，必须按视距放大补偿（`smoothstep(30,170)` 最多 3.2 倍），否则会在 mipmap 里被"吃掉"。

### 4.5 后处理链

```
RenderPass → GTAOPass → UnrealBloomPass(0.22/0.55/0.94) → OutputPass(ACES)
```

选 GTAO 而不是 SSAO 的原因很实际：SSAO 会自己重渲染一遍场景，丢掉色调映射，整幅画面发灰。GTAO 只做屏幕空间遮蔽，配合 ACES 输出，对比度正常。

Bloom 强度压得很低（0.22），只让天空和夜间灯光轻微溢出，避免"手游光污染"。

### 4.6 按需阴影与自适应分辨率

这两项是"操作不卡"的关键。

**按需阴影**：太阳每转过约 0.09°、且距上次刷新超过 0.2 秒才重画 shadow map（最多 5 次/秒）。省下的是一整遍全场景深度渲染——这是单帧里最贵的一步。

**自适应分辨率**：v1.1 改成“档位即实值”的兜底逻辑——启动 2.5 秒后每 0.8 秒统计一次平均帧率，只有低于 20 FPS 才在当前档位的 90% 以内降一点（每次 0.12），高于 45 FPS 再升回档位值（每次 0.07），两次调整至少间隔 1 秒。这样用户选「均衡」不会被偷偷降到 0.62。后处理缓冲同步跟随，避免 AO 与主画面分辨率错位。

### 4.7 雨雪独立场景

雨雪粒子不放进主场景，而是单独一个 `weatherScene`，在主渲染完成后叠加。原因是半透明粒子会污染 GTAO 的深度/法线预通道，在墙面留下黑白花斑。同样的坑还出现在"檐下 AO 面片"上——最终改为在墙体材质里按高度渐暗，而不是贴透明面片。

### 4.8 河道地形：在高度场里“挖”一条河

河道不是贴在地表的一层水，而是真的把地形切下去：

- 中心线从 (-105,-130) 到 (-98,130)，中段叠加两组不同频率的正弦（3.4·sin(0.019z) + 1.5·sin(0.047z)），外面乘 `sin²(πt)` 包络，端点位移与导数都归零，所以不会出现折角，也不会笔直像水渠。
- 河槽到岸顶的半宽 6 米，河谷影响半宽 9 米；河床恒定标高 −2.2 米，水位 −0.6 米。岸坡用 `sm01` 二次衰减，横截面按 0.5 米步长扫描，最大相邻高差 0.27–0.34 米，没有断崖。
- 地形网格只在 x∈[−118,−82] 把横向分段加密到 0.54 米，其余维持 3.26 米；净增约 1 万顶点，draw call 不变。
- 河床顶点色单独染成沙砾土黄，浅水能透出河底。

沿河 5 个 probe 点（z = −120 / −60 / 0 / 60 / 120）实测河床都是 −2.200 米、岸顶都是 0.000 米、下切 2.200 米、水位 −0.600 米、水深 1.600 米，完全一致。

### 4.9 山体与台地：抬升与压平要一起做

村东孤山用椭圆高斯式抬升叠加在原始高度场上：

- 中心 (170,20)，长短半径 75 / 68 米，旋转 −0.10 弧度，山顶抬升 58 米；山脚 x=95 处抬升为 0，山顶 x=170 为 58.000。
- 衰减用 `sm01` 的二次曲线，再叠加 fbm 噪声、放射状冲沟和北侧山梁，避免“馒头山”。
- 山体顶点色按抬升比例做三段混合：草 → 土黄 → 岩石，并与原来的“按海拔压暗”合并在同一个循环里，避免山顶发暗。
- 庙基与庙前老槐各有一块 `PADS` 台地：庙基 (140,20)、半径 4.8 米、过渡 14 米，台面标高 45.166 米；树盘 (147,28)、半径 2.6 米、过渡 7 米。40 级石阶按 `heightAt` 逐级落地。
- 阴影相机范围从原来的村域扩到 180 米见方（near 60 / far 520，中心 (70,0)），同时盖住村子与东山，否则山上的庙不会投影。

draw call 净增 8 个（庙按材质合批 7 个 + 石阶 1 个）。

### 4.10 水面：只用环境贴图，不做实时反射

水面是独立一层 `Mesh`，不是地形的一部分：

- 水位 −0.6 米，沿河道生成一条带状网格；`roughness 0.075`、`metalness 0.34`、`envMapIntensity 2.8`、`opacity 0.70`、`depthWrite false`。
- 反射直接取 `scene.environment`（现有田园 HDRI 经 PMREM 生成的 envMap），**没有 Reflector、没有 SSR、没有 CubeCamera 每帧重渲染**——实时反射在这个场景里太贵。
- 法线贴图复用现有 `TEX.water()`，每帧只滚 `offset.y`，模拟顺流而下的细碎波纹。
- 在 `onBeforeCompile` 里加了一项掠射角天光：按视角与法线的菲涅耳项，把 `skyUniforms` 的当前天色叠到水面上，所以近景能看到一串流动的亮斑，而不是一块哑光蓝板。
- 水面 `renderOrder = 2`，在 GTAO 之后绘制；精致档开 GTAO 时也没有黑斑或深度打花。

### 4.11 家畜：每只两个网格

原来的牛是“胶囊 + 方块头 + 四根圆柱腿”，每只 6–8 个 Mesh，16 只共 104 个 draw call。v1.1 重做为可信低模：

- 每只动物只有两个 Mesh：**身体**（躯干 + 肩峰 + 四条两段腿 + 尾巴 + 毛球）和**头**（脖子 + 椭球头 + 口鼻 + 耳 + 角/冠 + 眼）。
- 同种动物共享几何缓存，材质从“每个纯色材质 + 牛角单独材质”合并成 **1 个顶点色材质**；毛色按背深腹浅写入顶点色。
- 头是独立 Mesh，pivot 在脖子根，绕 z 轴周期下压做低头吃草（牛、羊约 24 秒一个慢周期，鸡快速啄食）。
- 尾巴用顶点属性 `aTail` 标记权重，材质 `onBeforeCompile` 按 `uTime` 缓慢左右摆，相位取世界坐标，16 只不同步。
- 结果：动物部分 draw call **104 → 32**，是改前的 0.31 倍；三角形数增加不多，观感从"一坨"变成能认出牛、羊、鸡。

### 4.12 风场：一份数据，四处可见

v1.1 的场景里风速只是一个数字，画面上看不出来。v1.2 第一项改动把风速与风向做成一套可共用的风场，并驱动四处效果。要点有三：

**一、数据先补齐。** 原始数据只取了 `wind_speed_10m`，没有风向。`tools/fetch-wind-direction.mjs` 用**与原始数据同一条 Open-Meteo 查询**补取 `wind_direction_10m`（8760 条），脚本会自校验：时间轴逐条一致、同次返回的风速与工程内逐值吻合（实测最大差 0.000 km/h），不通过就中止。写入采用文本级插入，保持原文件其余字节不变。

**二、口径统一到一处。** `climate.windAt(hour)` 是唯一出口：

- `speed`：m/s（原始单位 km/h，在此换算，消费方不再转）；
- `fromDeg`：气象来向，0=北、90=东；
- `dirX / dirZ`：世界坐标单位向量，指向**风吹去**的方向（世界坐标 +x 东、+z 南，与 `sunVector` 同一套）。推导：来向 θ → `dirX=-sinθ`、`dirZ=+cosθ`；自检 θ=270（西风）得 `dirX=+1`，吹向东。

整点之间用**最短弧**插值（`lerpAngle`）：这份数据相邻小时风向最大跳变 180°、P95 84°，线性插值会让旗子倒着绕一圈。

**三、渲染侧再做矢量低通。** `environment.js` 平滑的是风矢量的 x/z 分量而不是角度，所以风向翻转时矢量先减到接近 0 再朝新方向长起来（相当于一次风停），不会硬翻；时间常数 0.9 s。实测把时间轴瞬间从 0.7 m/s 跳到 9.17 m/s，风速在 9 个采样内单调爬升（3.49 → 7.26 → 9.17），没有突跳。

四处效果读的是**同一组 uniform 对象**（`world.windUniforms`），所以"方向一致"是结构保证，不是各处凑巧算对：

| 效果 | 做法 | draw call |
|---|---|---|
| 旗面 ×2 | 两面旗布合成 1 个 BufferGeometry、1 个材质；顶点着色器按 `uWindSpeed` 在"顺杆下垂"与"完全展开"之间绕水平轴旋转，再叠行波褶皱，最后绕杆转到 `uWindDir` | +1 |
| 草地（20 万株） | 改 `project_vertex`：位移落在**世界空间**。v1.1 是在对象空间加偏移，而每株草的实例矩阵里带随机 Y 旋转，于是各晃各的；相位用 `dot(世界xz, 风向)`，风浪顺风推进 | 0 |
| 作物（4.5 万株） | 同一注入器，走廉价分支（单个 sin + y² 衰减） | 0 |
| 雨丝 / 雪片 | `uWind` 单标量改为 `uWindDir` + `uWindSpeed`，xz 双向倾斜；雨丝尾迹方向与速度矢量同向，静风时竖直 | 0 |

两个实现细节值得记下来：

- **下垂位姿不能对两个位置做 `mix`。** 下垂时沿旗长与沿旗高都落在同一根竖轴上，布面会退化成一条线（实拍时旗子直接消失）。正确做法是绕"垂直于风向的水平轴"整面旋转，最大下垂角取 54°——再大就几乎贴杆、侧对镜头时看不见。
- **每株草的随机基础倾角必须小于风致位移。** 原本 ±0.34 rad（±19°）的随机倾角在 6 m/s 时会把风致方向盖掉，静止截图上读不出"风向统一"；收到 ±0.20 rad（±11°）后，配合更大的风致幅度，东风截图中草明显向右倒、西风明显向左倒。

### 4.13 炊烟：一张作息表，三处联动

v1.1 的村子里没有任何"人"的痕迹：天黑了窗自己亮，家畜 24 小时匀速踱步，屋顶上什么都不冒。这一版加的是**人的作息**。

**一、先建表，再接三处。** `js/schedule.js` 是唯一时间表：早饭 6.5–8.0、午饭 11.5–13.0、晚饭 17.5–19.0，窗灯 18.4–23.0，家畜出圈 6.6 / 归圈 18.8（全部是"当天小时"的连续值，由时间轴给出，不写死日期）。炊烟、窗灯、家畜都读它，不存在三套时间。

**二、同一户同一天结果可复现。** 某户这顿饭做不做，用整数哈希 `hash01(户序, 日内日序, 餐次)` 与概率比较得出：纯数学、无状态，重开页面或重跑构建结果都一样，换一天才重新洗牌。窗灯则是 `天黑 × 家里还醒着`——路灯仍是光控（天黑就亮到天明），窗灯是人控，23 点后陆续熄。

**三、烟本身是 GPU 算的。** 14 户 × 10 粒 = 140 个烟团合成**一个** `THREE.Points`，只占 1 个 draw call。上升、顺风漂移、湍流、膨胀、淡入淡出全在顶点着色器里按 `uTime` 求值；CPU 每帧只把「各户此刻的生火强度」写进预分配的 `aLevel` 数组，循环里不建任何对象。

四个踩过的坑，写下来免得下次重犯：

- **点尺寸不能拿常数当系数。** 第一版 `gl_PointSize = (0.5+age*3)*210/dep`，远看每个烟团只有 7 px，成了几个白点。正确换算是 `世界尺寸 × projectionMatrix[1][1] × 画布高 × 0.5 / 深度`——等价于 `1 米在 dep 米处占多少像素`，其中 `proj[1][1] = 1/tan(fov/2)`。
- **顺风漂移要用线性，不能用 age²。** 二次方在 9 m/s 时末端被吹出 14.6 m，10 个烟团之间拉开到 1.5 m 以上，整条烟变成一串珠子横穿半个村子。改线性并封顶 7 m 后，烟柱才是连续的。
- **烟色不能纯白。** 岷县早晨常是 100% 云量的白天空，纯白烟对着白天空实测几乎看不见；改成中灰 `0xc2c6c7` 并提高不透明度后，在亮天空与暗屋顶上都能读出形状。
- **暂停要冻结，这与其他环境动画不同。** 草摆、水波用 `performance.now()` 的纯 real-time，暂停照走；炊烟的时间 `smokeTime` 只在 `clock.playing` 为真时累加，暂停或拖动时间轴就定住。

烟囱本身顺手做了合并：v1.1 是逐户 2 个 Mesh（11 户有烟囱 = 22 个 draw call），这一版把 14 户的箱体与帽盖分别攒成 2 个合并网格，**净减 20 个 draw call**，同时给 3 户砖混补上了烟囱。箱体向下多伸 0.4 m，把原先箱底与屋面之间不到 6 cm 的缝埋掉。

### 4.14 数据卡：卡片数字与场景实例的一致性

「把介绍文字升级成结构化数据卡」这件事，难点不在加字段，而在**让卡片上的数字可被证伪**。

**一、先把归属补上。** v1.1 里 14 块地没有归属字段，16 头畜的 `owner` 只写了"李姓"这种随机姓氏——两项都无法对应到具体住户。这一版给 `FIELDS` 与 `ANIMAL_LIST` 各加 `ownerId`（H-01…H-14），家畜的 `owner` 同时改成「陈宅（3 号）」这种与户型对得上的写法。分配按尽量平均：H-09 空置户 0 亩 0 畜，其余 13 户各 1 块地、多出的 L-14 给人口最多的 H-06；16 头畜分给 13 户，3 户各 2 头、10 户各 1 头。

**二、卡片数字单独存，不现算。** `data.js` 里有一张 `HOUSE_CARDS` 表，写死每户的户主、耕地、牲畜、主要作物、年收入。这一点是刻意的：

- 若卡片在渲染时从 `FIELDS` 现算，"卡片数据"与"场景统计"永远相等，校验脚本就成了空转；
- 现在两边是**两份独立数据**，`tools/verify-cards.mjs` 按 `ownerId` 重新聚合场景侧，与卡片逐户比对，改了一块地的亩数却忘了同步卡片就会红。

负向自测：把 L-01 从 62 亩改成 66 亩，脚本报「亩数 卡片62 ≠ 场景66；收入 卡片20.3 ≠ 重算21.6」并以退出码 1 结束；还原后回到 0。

**三、年收入按公式推算。** 种植 = Σ(亩数 × 亩均净收益，按作物 1600–3200 元/亩)，养殖 = Σ(头数 × 60–4500 元/头只)，合计换算成万元/年、保留 1 位小数。费率表 `INCOME_RATES` 与 `estimateIncome()` 在 `data.js` 里，校验脚本复用同一个函数，口径只有一处。

**四、排版不动，窄屏折叠。** 新增的五行用与既有行完全相同的 `.row` 结构，外面套一层 `<details class="card-group">`：桌面端 `open`，折叠条 `display: none`，看起来与原来一字不差；窗口 ≤900px 时折叠条显形、默认收起，点标题展开。断点在 css 与 `matchMedia` 里各写一处，统一为 900px。

| 校验项 | 判据 | 失败示例 |
|---|---|---|
| 耕地亩数 | Σ(该户地块.area) == `farmland` | 亩数 卡片62 ≠ 场景66 |
| 牲畜数量 | 该户牲畜条数 == `livestock` | 牲畜 卡片1 ≠ 场景2 |
| 主要作物 | 亩数最大的作物 == `cropMain` | 作物 卡片当归 ≠ 场景党参 |
| 年收入 | `estimateIncome()` 重算 == `income` | 收入 卡片20.3 ≠ 重算21.6 |
| 空置户 | 常住 0 的户必须 0 亩 0 畜 | 空置户却分到了地或畜 |
| 全村合计 | 卡片合计 == 场景合计（513 亩 / 16 头） | 全村亩数 513 ≠ 517 |

### 4.15 同机位对比：不渲染第二遍

「同一机位、两个时刻」最直观的做法是同时渲染两遍，但那要多一套渲染通道，帧率直接腰斩。这里换了个思路：**A 不用实时渲染，抓成一帧位图存着**。

**一、A 是一张图，不是一台相机。** 进入对比时，在 `composer.render()`（以及雨雪的第二次叠加）之后、**同一帧内**把 `renderer.domElement` `drawImage` 到一张 2D canvas。时机很关键：WebGL 的绘制缓冲在浏览器合成之后就被清空，晚一帧拿到的是空白图。抓取尺寸与绘制缓冲一致，是 1:1 的像素复制，不经过缩放。

**二、分屏是裁切，不是双渲染。** 覆盖层是一个 `overflow: hidden` 的容器，宽度绑在 CSS 变量 `--ab-split` 上，里面的 canvas 固定 100vw 宽 —— 于是它只露出左边一段。改分割位置只是改一条 CSS 变量：

| 操作 | 样式重算 | 画面生效 |
|---|---|---|
| 滑杆 0→100% | 1.30 ms | 下一帧（15.8 ms） |
| 按住 Tab 全屏 A | 0.90 ms | 下一帧 |

远低于验收要求的 100 ms，而且**不触发任何渲染**，帧率不受影响。

**三、切换不会碰相机。** 因为 A 是位图、B 用当前相机，切换时相机根本没被读写，不存在阻尼回弹。为了把这条变成可自动核的事实，`afterRender()` 每帧把 `camera.matrixWorld` 的 16 个 float 与抓帧时存下的逐个比对，写进 `?qa=1` 面板的 `矩阵差` 字段，对比期间恒为 0。

这里有个必须记住的坑：**不能用 `Float32Array` 存这份矩阵**。`Matrix4.elements` 是双精度，存进 Float32Array 会被截断，逐位比较 16 个里有 11 个永远不相等 —— 看起来像"相机在动"，其实是精度假象。

**四、像素级对齐怎么验的。** 把 `world.update` 覆盖成空函数冻结全部 real-time 动画，然后：

- **同状态连抓两次**（间隔 3 帧）：0.396% 的像素不同，最大通道差 64 —— 这是帧间噪声本底；
- **A 与 B 跨时刻对比**（同机位、同画面）：0.412%，最大通道差 62 —— 与噪声本底同量级。

两者几乎相等，说明剩下的差异来自风矢量低通收敛尾巴带来的草地亚像素位移（时间相关），不是机位偏差。同一时刻左右分屏的截图上，接缝处的树冠、屋脊、道路完全连续。

**五、URL 复现。** `?ab=A` 与 `?ab=B` 共用同一组 `tx/tz/ty/r/phi/theta`，只有时间来源不同（A 用 `hour`，B 用 `bday/bhour`），所以"机位一致"由参数结构保证。`?ab=split` 会先按 A 抓帧、再切到 B 开分屏 —— 启动延迟 700 ms，因为页面加载前后浏览器有一次视口重排，那次 resize 会让刚抓的 A 尺寸对不上而立即判废。

### 4.16 生产性空间：六类物件，四个 Mesh

"像不像村子"很大程度取决于院外有没有生产痕迹。这一轮在院外背街一侧补了 6 处共享场院，共 16 个可点物件，六类分布是麦场 6 / 草垛 2 / 柴垛 2 / 粪堆 2 / 鸡窝 2 / 猪圈 2。每处场院由 2–3 户共用，覆盖 13 户在住户（H-09 空置不设）。

**数据先行。** `data.js` 的 `PRODUCTION` 每条带 `kind / category / yardId / sharedBy / pos / radius` 与卡片字段；`pos` 是世界坐标 `[x, y, z]`，单位米（+x 东 / +z 南），`radius` 是落位校验用的占位半径，单位米。麦场圆盘半径 3.60 m（⌀7.2 m）、面厚 0.06 m、16 块青石压边；草垛通高 2.30 m；柴垛 2.40 × 1.20 × 1.30 m；粪堆底半径 1.60 m / 高 0.90 m；鸡窝 1.60 × 1.20 × 1.10 m；猪圈 3.20 × 2.60 m / 栏高 0.95 m。把 `...PRODUCTION` 展开进 `ALL_OBJECTS`，拾取、档案卡、自检面板就自动接上——`objectById` 不需要改。

**合批策略。** 16 个物件的构件先按材质分进 4 个几何数组，`prodPaint(geo, tint)` 刷顶点色区分土/石/草/木的色差，`prodBake(list, geo, tint, p)` 按 `p.rot` 旋转再 `translate(p.pos[0], heightAt(...), p.pos[2])` 落到地形上，最后每组 `mergeGeometries` 成 1 个 Mesh：`production-soil`、`production-stone`、`production-straw`、`production-wood`。材质全部复用既有素材并 `clone()` 后开 `vertexColors`：土面用主路 `assets.road` 的夯土 PBR（初版误用 `TEX.soil()` 的田垄贴图，圆场看着像木条桶盖），石头用 `matStone`，草用 `detailMats.straw`，木用 `matWood`。只有草垛、木柴两组开 `castShadow`，阴影通道最多 +2。**没有新增任何贴图文件。**

**拾取与档案。** 16 个不可见代理盒（`PROD_PROXY`）进 `pickables`，不产生 draw call；`ui.js` 的 `SCHEMA.production` 给出 7 行字段（类别、用途、服务范围、尺寸、材质、使用时令、状态），`showCard()` 的副标题按 `category` 显示。`?qa=1` 增加一行 `production 16 个 / 6 处场院 / 4 组合批 Mesh`。

**草层不重排。** 场院下面不能长草，但撒点循环里插 `continue` 会改变随机数的取用次数，导致后续 15 万株草位整体重排——整个村子的草地会变样。做法是照常取完随机数、算完位置，只在 `m4.compose()` 时把落在 `inProduction(x, z)` 占位圆内的实例缩放写成 0；`prodFoots` 由同一份 `PRODUCTION` 计算，改坐标时数据与几何天然同步。

**落位校验。** `tools/verify-production.mjs` 是纯 Node 脚本，不依赖 three / DOM / 网络：按主路折线中线 `roadX(z)`（半宽 3.1 m 加路肩余量）避让道路；耕地带 `rot`，`distRect()` 必须把点反变换到地块局部坐标再算净空，轴对齐矩形近似会误判；此外还查院墙、公共设施、水窖、石墩、石碾、树干、电线杆脚与两两间距。实测到最近障碍净空 0.51 m、与耕地最小净空 0.83 m（P-03 ↔ L-11）。负向测试把 P-01 挪进 L-01，脚本报「净空 −3.60 m」并以 1 退出，还原后回到 0。

**不接时间轴。** 这 16 件都是静态陈设，没有随时间变化的效果，因此不进 15 分钟一格的时间轴；硬约束里"随时间变化必须接时间轴"在这轮不触发，黄金路径的拖动行为也不受影响。

**验收读数。** `?quality=low&scale=0.75` 同机位、受控隐藏 4 个 `productionMeshes` 前后对比：draw call 增量 **+4**（要求 ≤8）、三角形 **+3,648**；A 基线 712 calls / 3,045,279 tris / 56.5 FPS，B 版 710 calls / 3,049,991 tris / 46.7 FPS（该次 4 s 窗口）。绝对总数会随视锥、家畜相位与无头环境波动，所以增量以受控开关为准；按项目约定不做 FPS 数值断言。16 张档案卡逐张打开均为 7 行、右上角 `×` 与点空白关闭正常，第一人称沿主路无压路、无穿墙。

### 4.17 公共核心：从「物」到「场所」

13 处公共设施里 6 盏是路灯，剩下的也多是水井、磨坊、宣传栏这类「物件」。缺的是一个能让人认出来的**村中心公共区域**。这一轮的做法是：既有的 `F-02` 村委会原址升级（补 3.40 × 1.50 m 村务公示栏，9.5 m 旗杆与二层楼保留），再新建 4 处独立可点场所。任务里「戏台或文化广场」按用户选的「都要」实现为两处独立对象，因此公共核心共 **5 处**、可点对象 188 → **192**。

| 编号 | 场所 | 位置 `(x, z)` m | 占地 | 辨识特征 |
|---|---|---|---|---|
| C-01 | 小卖部 | `(40.00, -13.00)` | 7.0 × 5.0 m / 35 ㎡ | 砖木平房、红瓦双坡顶、手写感招牌、窗台塑料筐 |
| C-02 | 卫生室 | `(33.00, -31.00)` | 8.0 × 6.0 m / 48 ㎡ | 白墙平顶、女儿墙、山墙白底红十字 |
| C-03 | 戏台 | `(-36.00, -4.00)` | 9.0 × 6.5 m / 58.5 ㎡ | 砖砌台基、四木柱、青瓦顶、「同乐台」匾额 |

**数据口径。** `data.js` 的 `CIVIC` 每条带 `kind / category / pos / footprint / radius / area` 与卡片字段；`pos` 为世界坐标 `[x, y, z]`，单位 m（+x 东 / +z 南，`y` 恒为 0，标高由 `heightAt()` 取）；`footprint` 为 `[x 方向长, z 方向宽]`，单位 m；`radius` 是外接圆占位半径，单位 m，须 ≥ 半对角线；`area` 单位 ㎡ 且必须等于 `footprint` 两维之积。`F-02` 补 `population: 43`（人）与 `farmlandTotal: 513`（亩），分别等于 `ΣHOUSES.residents` 与 `ΣFIELDS.area`，与任务 03 的 `verify-cards.mjs` 同一套 Σ 算法，不允许两处写死不同数字。`...CIVIC` 展开进 `ALL_OBJECTS` 后，拾取与档案卡自动接上——`objectById` 不需要改。

**合批策略。** 与 4.16 同一套做法：`civicWall / civicRoof / civicWood / civicStone` 四组几何用 `mergeGeometries` + 顶点色合成 4 个 Mesh。墙体新建一个 `MeshStandardMaterial` 复用 `matPlaster.map / normalMap / normalScale` 再开 `vertexColors`；屋顶用 `matRoof.clone()`，但 three r160 的 `Material.copy()` 不复制 `onBeforeCompile`，所以克隆后手动把 `onBeforeCompile` 与 `customProgramCacheKey` 挂回去，否则戏台/小卖部的坡顶会丢掉雪/湿 uniform，下雪天与全村其他屋顶不一致。第五个 Mesh `civic-signs` 用一张程序化图集装下四个标识。`js/textures.js` 的 `civicSigns()` 在 1024×512 canvas 上画成四格（每格 512×256）：小卖部手写招牌、卫生室红十字、村委会村务公示栏、戏台「同乐台」匾额；`civicSign(col, row, w, h, ...)` 按格写 UV，四个面片合进同一个 Mesh，**只占 1 个 draw call，不新增任何贴图文件**。建筑构件全部用现有 `Box / Cylinder / PlaneGeometry` 拼装，不做高模。

### 4.18 地形材质：按坡度、高度、曲率混草土石

**为什么改。** 原来整块 620×620 m 地形只采一张 `assets.grass`、`repeat=300`，全图同一个 2.07 m 周期；`patchSeason` 的 macro 只能调亮度，改不了图案本身，近景必然看出重复。山体更糟：顶点色把同一张草地贴图乘成土黄与冷灰，山顶读不出岩石。

**三层。** 草 `assets.grass`（2.07 m）、土 `assets.road`（4.50 m，UV 转 +27°）、石 `TEX.terrainRock()`（26.00 m，转 −41°）。三个周期比 1 : 2.17 : 12.6，互不成整数比，三张图的平铺网格不会同时对齐；再叠 macro 的 3.7 / 11.3 / 28.9 三层。村内 `f=0` 只有草层，再叠一层 7.90 m 的同向第二尺度（权重 0.18）打散 2.07 m 的重复。

**权重。** `terrainWeights()` 逐顶点算草/土/石三个权重写进 `aTerrW`（vec3，46,986 顶点 ≈ 564 KB），三个信号：
- 高度 `f = hillLift / HILL_LIFT`，0 = 村内、1 = 孤山顶；分界线加 ±0.035 的低频噪声，避免完美等高线
- 坡度 `1 − 法线.y`
- 曲率：三角形邻接的顶点拉普拉斯 ÷ 边长² × 40，clamp ±1（`d` 取三边均值，河道加密带的 0.54 m 短边不会放大 36 倍）

```
wRock = smoothstep(0.42,0.92,f) × (0.55 + 0.45·slopeW) + 0.35·slopeW·smoothstep(−0.10,0.60,curvN)
wSoil = 0.75·smoothstep(0.10,0.48,f)·(1−wRock) + 0.25·smoothstep(0.15,0.75,−curvN)·(1−wRock)
wGrass = 1 − wRock − wSoil
```

其中 `slopeW = smoothstep(0.015, 0.30, slope)` 是坡度加速项，`wRock` 上限 0.72（满格会让整座山读成石墙）。阈值按 46,986 个顶点的实测分布标定：坡度中位 0.011 / p90 0.077、曲率 p10 −0.0136 / p50 0 / p90 0.0132。若按「常见陡坡 0.3」判岩石，全图只有山顶几十个顶点命中、山会整片变绿，所以坡度只作加速项、主判据是 `f`。

**顶点色只留两件事。** 原来 `SOIL=[1.52,1.18,0.72]` / `ROCK=[0.92,0.98,1.95]` 那套色偏是「给同一张贴图上色」，现在材质分带由三层权重接管，再乘一遍会让裸土与岩石过饱和；所以顶点色只剩海拔压暗与河床沙砾。

**兼容昼夜与天气。** 三层只决定 albedo / 切线空间法线 / 粗糙度，光照仍由 `sun / hemi / moon + scene.environment` 驱动，昼夜自动生效；积雪仍在 `diffuseColor` 之后混白，并把法线按 `uSnow × 0.95` 拉回几何法线（0.75 时雪面还会透出石层凹凸、读成方格网）；湿润压暗不变。

**LOD。** `uTerrLodNear/Far` 以内走完整三层（颜色 3 + 草层第二尺度 1 + 法线 3 + 粗糙度 3 采样），过渡带淡出；之外只保留**三层颜色**、法线与粗糙度退回单层。三档只改距离：低 30/48、中 36/58、高 44/70，层数不变。远景保留三层颜色是实测结论——山体离相机总有 100+ m，按距离把材质一起降级会让整座山永远只剩一张 grass 的 mipmap 平均色。

**成本与校验。** 地形仍是 1 个 Mesh / 1 个材质，draw call 与三角形增量 0；三档 FPS 与基线持平（low 三次中位 45.6 vs 45.1）。`tools/verify-terrain.mjs` 纯 Node，校验 `aTerrW` 结构、三个世界周期与比值、三档 LOD、`TERRAIN` 常量顺序，并用独立复刻的权重公式验算归一、单调与特征点。

### 4.19 作物物候：五状态、四形态族、一份积温

**为什么重做。** 原来 14 块地虽有 6 种作物，但共用一个 InstancedMesh、一张交叉面片，只有 0.28–0.56 m 的高度差和色相差；`stage` 是写死的档案文字，`uGreen` 只做连续缩放——「成熟」和「收割后」画面上没区别，也没有「休耕」。

**五状态。** 每块地 `g = clamp((积温 − 播种日积温) / gddNeed, 0, 1.10)`：

| `g` | 状态 | 株高系数 | 密度 | 色相 |
|---|---|---|---|---|
| ≤ 0.001 | 休耕 | 0 | 0 | — |
| 0–0.12 | 出苗 | 0.06→0.18 | 0.35→0.75 | 嫩黄 |
| 0.12–0.72 | 生长 | 0.18→0.92 | 0.75→1.0 | 深绿 |

密度不是布尔开关：每个实例带一个固定随机阈值 `aRand`，`vis = smoothstep(aRand−0.08, aRand+0.08, den)`，所以出苗与收割时是按顺序逐渐长出来 / 消失，不会整片闪。

**校验。** `tools/verify-crop.mjs` 纯 Node，独立复刻状态函数：14 块地 / 513 亩、当归恰好 2 块、8 种作物都有 `CROP_SPEC`、四族都有作物、播种后积温够走完全生育期、五状态齐全且形态在边界连续（`g` 步进 0.001 时最大跳变 0.0095）。

### 4.21 树木四形态：一套骨架，四种轮廓

**为什么改。** 95 棵树共用同一套骨架 —— 3 根主枝 + 各 3 根二级枝，枝条倾角 0.42–0.88 rad 随机，五种树只差 `height / canopy / dbh` 三个数字。俯瞰时几乎一个样，也看不出杨、柳、槐、榆的区别。更要紧的是树段用的是 `Math.random`，每次刷新长出来的枝都不一样。

**四种轮廓。** `TREE_FORM` 四套参数，只作用于实例矩阵与叶簇分布，几何仍是同一份圆柱 + 叶面片：

| 形态 | 树种 | 干高比 | 冠椭球（× canopy） | 主枝倾角 | 叶簇系数 |
|---|---|---|---|---|---|
| `poplar` | 杨 | 0.58 | 0.28 / 0.78 / 0.28 | 0.22–0.44 | 1.32 |
| `willow` | 柳 | 0.34 | 0.74 / 0.32 / 0.74 | 0.55–0.85 + 下垂 0.86 rad | 0.62 |
| `locust` | 槐、杏 | 0.42 | 0.62 / 0.56 / 0.62 | 0.50–0.82 | 1.22 |
| `elm` | 榆 | 0.54 | 0.46 / 0.70 / 0.46 | 0.42–0.72 | 0.82 |

干高比顺序 杨 > 榆 > 槐 > 柳：杨的冠抬得最高、枝条几乎贴干向上，整棵像一根柱子；榆次之但枝条向外张；槐冠最低、近球形；柳最矮、冠扁而宽。

**垂柳。** 主枝第 1 段按 0.55–0.85 rad 上扬，之后每段用 `droopDir()` 把方向绕水平轴向下压 0.86 rad（第 3 段约 −40°），段长递增到 0.90、半径递减到 0.70。每一段末端往下挂 2–3 串叶簇（靠下的段挂 3 串），形成垂帘；柳叶用 `leafAspect [0.58, 1.32, 1]` 拉成细长形。

**按区位分配。** `pickSpeciesFor(x, z, seq)` 是纯函数、不消耗随机数：主路行道（`|Δx 主路| < 14`）杨 70% / 榆 20% / 槐 10%；院落周边槐 40% / 榆 40% / 杏 10% / 杨 10%；河边（`|Δx 河| < 26`）每 6 棵留 1 棵杨、其余全柳。为什么不在这里取随机数：树的坐标、民居、场院、作物全串在同一条全局随机序列上，这里多取一个就会把后面所有布局整体推移 —— 所以 `addTree()` 里仍保留一次 `rnd()` 调用对齐消耗，只是结果丢弃。

**可复现。** 树的随机数换成每棵树独立的 `treeRng(seed)`（mulberry32），种子 = 位置毫米哈希 ^ 序号。同一份数据每次加载长出来的枝与叶逐位一致；改一棵树的位置也不连累别棵。连续两次加载同一页面，树干实例矩阵指纹与叶簇数完全相同。

**绘制批次。** 仍是干 / 枝 / 叶 3 个 InstancedMesh，draw call 与树种数无关（任务上限 +4，实际 0）。干 101 / 枝 1,695 / 叶 38,943。

**校验。** `tools/verify-tree.mjs` 纯 Node：101 棵树 / 198 对象、五种 kind、区位比例、四套参数、柳树 droop、干高比顺序、`FORM_OF` 覆盖、没有树落在河道、`treeRng` 可复现、树段里没有 `Math.random` 与全局 `between`、干枝叶 3 组实例。`--self-test` 把 10 棵河岸柳挪进村（柳占比降到 67%）确认会报错。

### 4.22 野性层：山坡田边的灌木与杂草

**为什么加。** 地形材质改完后，山坡只有草/土/石三层贴图，田边只有一条几何田埂，村后孤山从山脚到山顶一根植被都没有——画面太"整洁"。本轮新增「野性层」：灌木 8000 丛 + 杂草 14000 丛，全部实例化、低模、随距离淡出，近景有前后层次（近处杂草 → 中景灌木丛 → 远山）。

**几何。** 灌木 = 3 片交叉叶卡 + 顶盖 + 二十面体核心块（共 28 三角形），顶点带 `aCore`；杂草 = 8 片细窄弧形叶（根宽 0.013 m → 梢 0.0025 m，纯顶点色）。近景杂草 0.35–0.95 m，比实体草高一档。

**撒点。** 密度 = 六路权重取最大值（陡坡 0.85 / 孤山 0.70 / 河岸带 0.90 / 田埂带 0.55 / 田边带 0.85 / 村周 0.22，平地底噪 0.10）× fbm 斑块（0.030，簇与空档）× openness 稀疏系数（主路 2.2 m / 巷 1.6 m / 院墙 3 m / 场院 2 m 内趋近 0）。耕地、道路、场院、公共核心、河道、田埂路面全部排除。随机数 `treeRng(0x5C2B17)`，不消耗全局 `rnd`，逐位可复现；加载时一次算完，运行时每帧 0 CPU 开销。

**季节。** 春夏青绿、秋冬枯黄褐，接 `seasonUniform`。灌木乘色（保叶卡层次）、杂草按亮度重建色相（乘色会把枯草顶成惨白）。积雪按局部高度扫白，共用 `uSnow`。顺坡倾斜 65% + 下沉 0.12 m，坡上不露悬空的根。

**远景。** 顶点着色器按距离把叶卡塌缩进核心块（42–58 m，`mix(1.0 − _lod, _lod, aCore)`），120–175 m 整体淡出，杂草 30–46 m 淡出；淡出距离全走 `uScrubRange` uniform。远景山体一根都不画，观感与改造前一致。

**绘制批次。** 灌木、杂草各 1 个 InstancedMesh，`castShadow = false`，draw call 增量 **+2**（任务上限 ≤2）。受控开关精确单帧实测 1050 → 1052 calls，三角形 +672,000。

**校验。** `tools/verify-scrub.mjs` 纯 Node：`SCRUB` 常量（数量/种子/三对淡出距离/区域覆盖）、draw call 预算、撒点规则与排除判定、季节两套配色接线、`aCore` 塌缩与 `uScrubRange`、`treeRng` 可复现、QA 行。`--self-test` 内存里做三项破坏（实例换普通 Mesh / 对调淡出距离 / 拿掉乘色配色）确认 3/3 报错。

### 4.23 牲畜微动作：按种类循环动作与雨雪避檐

**为什么做。** 16 头牲畜（牛 4 / 羊 6 / 鸡 6）虽有踱步与低头吃草，但牛缺少反刍、鸡的低头是连续正弦更像点头，而且雨雪天原地淋雨不合理。本轮给每种动物一套循环微动作，另按用户要求**新增一只看门狗**（任务约束 draw call 不增加，经确认放宽 +2 给狗用）。

**种类动作**（全部走顶点着色器与每帧 CPU 旋转，没有逐头 AnimationMixer / 骨骼）：

| 种类 | 动作 | 参数 |
|---|---|---|
| 牛 | 反刍：不吃草时头微抬、颌部水平慢摆（夜里也倒嚼） | 0.5 Hz × 0.05 rad |
| 羊 | 低头吃草 + 侧向拉草 | 0.40 Hz × 0.10 rad |
| 鸡 | 「双啄一停」锐脉冲 + 啄时身体前倾 | `pow4` 锐化，约 2.4 s 一啄、啄程 0.3 s、前倾 0.06 rad |
| 狗（新增 A-17） | 卧姿，偶尔抬头张望 + 呼吸 + 摇尾 | 抬头 0.55 rad / 约 48 s 一周期；呼吸 ±1.2%；摇尾 2.6 Hz × 0.35 |

尾巴摆频 `aFreq`（Hz）与摆幅 `aWag` 做成几何属性喂给共用 `matHide` 的顶点着色器：牛/羊/鸡保持 1.15 Hz × 1.0 与 v1.1 逐位一致，狗 2.6 × 0.35。所有动作乘作息表活动量 `herd`，入夜归零。

**雨雪避檐。** 判定与 `updateWeather` 同口径（雪量 > 0.01 或降雨 > 0.05），由 `climate.sample(hour)` 驱动、跟时间轴。避雨点在 `buildAnimal` 时算好：牛羊 → 东头畜圈 F-03 `[46, 34]` 檐下半径 4.5 m 按序号错开角度散开，鸡 → 就近鸡窝（P-13 / P-14）旁 0.9 m，狗 → 赵宅院墙根外 0.65 m；全部 `heightAt` 贴地。位置按平滑因子 `wetK` 过渡（约 8 s 实时走完），到站后站立环视、不再吃草踱步。

**暂停口径（写明并保持一致）。** 摆尾 / 啄食 / 反刍 / 呼吸用实时钟，时间轴暂停时**继续**——环境动画口径，与草、旗面、水面法线一致；避雨过渡受 `clock.playing` 门控，暂停即**定住**（同炊烟口径）。`update()` 签名扩为 `(hour, climate, playing)`。

**随机序列零消耗。** 狗的档案字段、朝向（−0.12 rad）、动作相位（写死 3.3）全部不调用 `between/rnd`，其后公共设施等随机细节与上一版逐位一致；`ANIMAL_LIST` 16 → 17（A-17 归赵宅 H-05，卡片牲畜 2），`INCOME_RATES.animal.狗 = 0` 不进养殖收入。

**绘制批次。** 每只仍是身体 + 头 2 个 Mesh 共用 `matHide`，狗 draw call 增量 **+2**（放宽额度正好用满）：受控开关精确单帧实测 1055 → 1057 calls，三角形 +2,028。

**校验。** `tools/verify-livestock.mjs` 纯 Node：计数与档案（17 头 / A-17 归 H-05 / 狗收入 0 / 落位公式）、draw call 预算（每只 2 Mesh、无混合器与骨骼、`aFreq × aWag` 属性）、种类动作常量、雨雪避檐（判定口径 / `wetK` 平滑 / `playing` 门控 / 避雨点贴地）、暂停口径注释、随机序列零消耗、QA 行。`--self-test` 三项破坏（暂停门控失效 / 狗摇尾退化成牛尾 / 雨雪判定恒 0）3/3 抓到。

### 4.24 旱作元素：地膜、篱笆与田埂

**为什么做。** 西北旱作农业最有辨识度的三样东西——铺膜、围栏、打埂——场景里都缺：田面只有作物实例和一张土贴图，地块边界只是贴图差异；村里原有 11 段随机散落的篱笆，不围任何东西。本轮按「只在播种期出现、与 09 作物状态联动」的要求补齐。

**地膜。** 1 个 InstancedMesh 共 232 条带（带宽 1.10 m、带间隔 0.35 m、长 = 田长 − 1.2 m），每实例带 `aFieldIdx`，顶点着色器读作物轮同一份 `uFieldG[14]`（每帧只写 14 个 float）：覆盖度 = 播种淡入（g 0.001→0.02）× 出苗揭膜（1 − smoothstep 0.10→0.20）——实测当归 day 115 铺上、约 day 152 揭完，休耕与收割后没有，跟时间轴不写死日期。颜色按作物写实：当归 / 党参 / 柴胡 / 黄芪 / 马铃薯**黑膜**（岷县药材黑膜压草的标准做法）、玉米 / 蔬菜**白膜**（全膜双垄沟）、**小麦不覆膜**（条播）。防 z-fighting 双保险：膜面在田面上方 0.012 m + `polygonOffset −2`；收起时条带在顶点着色器里缩放塌缩成一点，无透明排序问题。`?nocrop` 时与作物一并跳过。

**篱笆。** 木栅围住两块蔬菜地（L-05「门前菜地」、L-13「门前园子」），栅栏线在田埂外 0.8 m：立柱每约 2.2 m 一根（高 1.25 m、埋深 0.15 m）+ 双横杆（0.52 / 0.92 m），合计 237 m。树枝栅质感用顶点色微差（亮度 ±6%，序号 hash 确定，**不消耗随机序列**）。原先 11 段随机散篱笆（66 个 Mesh）拆除，但保留了它们的 `between()` 消耗——其后随机细节零位移。

**田埂。** 14 块地 × 4 条边埂保留闭合环（**地块间边界连续不断头**），新增宽窄随地形：每边外沿中点采地形高差，下坡侧（外埂，易被雨水冲垮）在 1.5 m 高差内线性加宽 0.5→0.7 m、加高 0.34→0.42 m。56 条埂合并成 1 个 Mesh（改造前是 56 个独立 Mesh = 56 draw call）。

**绘制批次。** 新增绘制对象 3 个（田埂 1 + 篱笆 1 + 地膜 1，任务上限 ≤4）；受控开关精确单帧实测 964 → 967 calls（+3 / +3,648 tris）。同机位与上一轮比**净减 90**（拆除散篱笆 −66、田埂合并 −55）。地膜与栅栏均不进拾取（`pickables` 保持 199）。

**校验。** `tools/verify-farm.mjs` 纯 Node：田块数据（14 块 / 蔬菜地恰 L-05 / L-13）、田埂合并与宽窄口径、地膜（InstancedMesh 唯一 / `uFieldG` 接线 / 覆盖度公式 / 抬高与 polygonOffset / 小麦排除 / 黑白 instanceColor / `?nocrop`）、篱笆（围蔬菜地 / 0.8 m / 双横杆 / 柱距 / 合并 / 散段拆除且 `between()` 保留 / hash 不消耗 rnd）、新增对象恰 3、QA 行。`--self-test` 三项破坏（z-fight 防护失效 / 地膜恒显 / 田埂逐 Mesh 回潮）3/3 抓到。

### 4.25 气象数据面板：把 8760 条实测画出来

**为什么做。** 数字孪生最实的落点是把气象数据本身展示出来。modebar 新增「气象」按钮，右侧滑出全年气温与降水面板：橙色日均温折线（左轴 ℃，含 0℃ 冻线虚线）+ 蓝色日降水柱（右轴 mm），一眼能读出岷县的年温度周期与 5–9 月雨季集中度。

**数据与降采样。** `data/` 的 8760 条逐小时实测一次性预算成 365 个日均温与日合计降水（`buildStats`，单位 ℃ / mm）；绘制时按画布宽度降采样——像素列 x 对应日序 `x / w × 365`，取相邻两天线性插值，画布多窄都不丢趋势。降水柱按 `barPitch = max(3, round(w/160))` 像素聚合，柱高画窗口日均避免聚合窗大小不同导致的高矮失真。

**双向同步。** 拖时间轴 / 播放 → `main.js` 动画循环每帧调 `updateClimateChart(clock, wx)`，内部以「游标 x 像素变化 ≥1」为闸门，静止画面零重绘；点 / 拖曲线 → `clock.hour = round(fx × 8760 × 4) / 4`（对齐 15 分钟一格，与时间条 `TIME_STEPS = 35040` 同分辨率），时间条滑块经既有回写逻辑跟随，离开天气预设时刻自动取消高亮。游标旁显示当前日期时间与实测温度（逐小时插值，与场景同源）。

**按需重绘。** 静态层（曲线 + 柱 + 刻度）画进 offscreen canvas，只在打开 / resize 时画一次；可见层重绘 = 一次 `drawImage` + 一条游标线 + 一行小字。重绘计数暴露在 `__app.chartRedraws()`：打开面板 → 1，暂停静置 4 秒 → 仍为 1，改一次时刻 → 恰好 2，同像素内微调 → 不重绘。面板开合 draw call 逐位相同（960），FPS 差 0.1（验收线 < 2）。

**模块。** `js/climate-chart.js` 零 import（Canvas 2D 自绘，无图表库、无 three 依赖），模块数 11 → 12。`?nocrop` 不影响面板（面板读的是原始数据，不是作物实例）。

**校验。** `tools/verify-climate-chart.mjs` 纯 Node：DOM 接线、自绘零依赖、数据源字段、按宽度降采样、offscreen + 游标闸门 + 计数、点击对齐 15 分钟格、拖动、`main.js` 接线。`--self-test` 两项破坏（每帧全量重绘 / 删点击跳时刻）2/2 抓到。

### 4.26 教学视图：标注层与河谷剖面

**为什么做。** 面向教学场景需要两个默认关闭的辅助视图：一是把地名 / 地块编号 / 等高线「贴」到场景上的**标注层**；二是把河道横截面「剖」出来讲下切与水位的**剖面视图**。两者与第一人称、巡游互斥。

**标注层。** 24 个标签（地名 10 + 地块编号 L-01…L-14）画进一张 1536×384 canvas 图集，1 个 InstancedMesh 面片（3.6 × 1.35 m，锚点在对象上方 2.6 m）= 1 draw call；UV 通过 `aUvRect` 属性从图集槽位取。**图集必须关 mipmap**——1536×384 非二次幂 + mipmap 在 ANGLE-on-Metal 下会得到一张全透明空纹理（缺陷已写进 verify-teach 回归锁）。等高线在地形 shader 内：`uContour` 开关、每 2 m 一条、`fwidth` 抗锯齿，0 draw call。

**剖面视图。** 裁剪平面 z = −60（保留南半村域、切面垂直河道流向）：开启时遍历场景给 102 份材质挂 `clippingPlanes`，关闭全部还原 `null`。剖面填充面 1 个 quad（24 × 6 m）贴在切线上，CanvasTexture 按 `heightAt(x, −60)` 逐列采样画河床轮廓与表土 / 心土 / 基岩三层，水体半透明覆盖 bed→水位区间。三个尺寸标注（下切 2.2 m / 水位 −0.6 m / 水面宽 8 m）**直接读 `RIVER` 常量**（水面半宽对 `riverHeight == waterY` 数值求解），与 CHANGELOG 数值天然一致。开启剖面会保存 rig 机位并移到观察位，关闭时恢复——场景完全复原。

**互斥与绘制批次。** 进入第一人称（按钮 / F 键）与巡游前三处入口都会 `closeAll()` 并提示。新增绘制对象 2 个（标注 1 + 剖面填充 1，上限 3；等高线 0）：受控开关实测默认 277 calls → 剖面开 31（北半被裁，预期）→ 关闭 277 与基线逐位相同；十次开关后裁剪残留 0、FPS 回满帧。

**校验。** `tools/verify-teach.mjs` 纯 Node + `--self-test`（3/3：关闭不还原裁剪 / 标注写死数值 / 标签拆成逐个 Mesh）。

除上表对象外，地形层还有两项不属于“可点击对象”的内容：村西河道（宽 8 米、下切 2.2 米、常水位 −0.6 米、漫水桥）与村东孤山（山顶 58 米、45.17 米台地上的山神庙 + 40 级石阶）。主路沿线另有 8 根水泥电线杆与简化架空线（不做碰撞、无档案卡），杆位贴地形、导线按 0.62 m 下垂生成。

生产性空间的分布规则见 4.16：每处场院 2–3 户共用、覆盖 13 户在住户，院外背街一侧，鸡窝猪圈贴院墙（净距 0.2–1.8 m），与耕地最小净空 0.83 m。公共四处场所的落位与口径见 4.17。

### 5.2 建筑与院落

每栋民居由 20 余个构件组成：台基、墙裙、墙体、屋面、屋脊、檐口椽头、门框门楣、门槛、门扇、窗棂、窗台、烟囱帽、院墙、墙帽、门楼。院内按西北农家习惯布置晒架（秋晒药材）、柴垛、水缸、架子车、粮囤，并按 `doy` 切换晾晒物——9 月中到次年 1 月晒当归，其余时间挂辣椒串。

### 5.3 档案字段

各类型对象的字段见《管理员手册》4.3，其中生产性空间（`production`）是 7 行，公共核心（`civic`）是 8–9 行（戏台与文化广场多一行「使用时令」），`F-02` 村委会另加「全村常住人口 / 全村耕地总面积」两行。所有字段都来自 `data.js`，没有后端、没有数据库。新增类型必须在 `ui.js` 的 `SCHEMA` 里注册，否则 `showCard()` 会降级成 `facility` 的默认字段。

## 六、视觉与体验设计

### 6.1 光照曲线

| 时段 | 判据 | 表现 |
|---|---|---|
| 白天 | 太阳高度 > 11° | 直射为主，天光 0.34，曝光 0.94 |
| 暮光 | −6° ~ 11° | 曝光抬到 1.0 以上，天光转暖，路灯与窗灯渐亮 |
| 夜晚 | 太阳低于 −6° | 月光 0.95 冷蓝补光，天光 0.13，曝光 0.74 |

黄昏最容易翻车：如果只按太阳高度线性衰减，画面会在半小时内从白天直接掉进黑夜。所以加了**暮光补偿** `twi = exp(−(sinAlt/0.13)²)`，在太阳贴地时抬高天光、曝光与环境反射强度；同时天空用独立的 `skyF` 曲线——地面先暗、天还亮，才有剪影感。

### 6.2 天气表现

| 天气 | 表现 |
|---|---|
| 晴 / 少云 | 云覆盖度低，太阳硬，阴影清晰 |
| 阴 | 云覆盖度接近 1，天空压灰，阴影变软 |
| 雨 | 1300 条雨丝、路面变暗、雾加浓 |
| 雪 | 900 个雪点、72 小时累计积雪覆盖屋顶与地面、气温回升后融化 |
| 雾 | 湿度 > 78% 时雾密度上升 |

界面上的「晴 / 阴 / 雨 / 雪」不是写死日期，而是每次启动时从 8760 条记录里现算：晴取“云量 <10%、无降水、9–16 点、夏季最热”，阴取“云量 >85%、无降水、夏季正午前后”，雨取“全年降水量最大的一小时”，雪取“气温 <0℃ 时雪量最大”。换一份数据文件，四个按钮会自动落到新数据里对应的极值时刻。当前数据算出的四个时刻是：

| 预设 | 时刻 | 依据 |
|---|---|---|
| 晴 | 2025-07-30 15:00 | 云量 2%，26.4℃ |
| 阴 | 2025-06-03 13:00 | 云量 100%，10.8℃ |
| 雨 | 2025-09-05 02:00 | 降水 8.2 mm/h（全年最大，夜间） |
| 雪 | 2025-03-05 11:00 | 降雪 0.63 cm，−0.5℃ |

### 6.3 相机与操作手感

- 旋转：时间常数约 50 ms（`1−exp(−dt·20)`），跟手但不硬切
- 缩放：约 110 ms（`k=9`），滚轮按 `deltaMode` 归一化，触控板小增量不会被放大
- 注视点：约 180 ms（`k=5.5`），聚焦时有推进感
- 行走：起步 110 ms、收步 80 ms，Shift 加速时视野从 68° 推到 74°
- 巡游：每段用 `easeInOutCubic`，段内缓入缓出；段与段之间硬切，靠字幕 120 ms 淡出淡入过渡

所有阻尼都用 `1−exp(−dt·k)`，与帧率无关——60 Hz 和 120 Hz 上手感一致。

### 7.2 优化清单

1. 阴影按需刷新（最大收益）
2. 植被全部实例化，草地 20 万株只占 2 个 drawcall（基础层 + 近景层）
3. 家畜每只合并成 2 个 Mesh，16 只从 104 个 drawcall 降到 32 个
4. 民居门窗构件按“一套几何 + 14 个实例矩阵”合并，只加 2 个 drawcall
5. 石墩 5 只合并 1 个 Mesh；水窖按石/铁/木三种材质各合并 1 个
6. 悬停拾取限频到 11 Hz，且拖动时不做
7. 时间条 DOM 写入限频到 9 Hz，文字没变不写
8. 积雪/湿润按 1/12 小时缓存，省掉每帧 28 次气象取样
9. 后处理尺寸跟随渲染倍率，避免高分辨率下的隐性超采样

### 7.3 实测

用 git 检出 v1.0 与当前 v1.1 各起一个本地服务，同一台机器、同一机位（村中心 120 米环视，phi 0.9）、同一分辨率 1280×720、固定像素比 1、精致档，测同一段脚本：

| 指标 | v1.0 | v1.1 | 变化 |
|---|---|---|---|
| 可点对象 | 160 | 172 | +12 |
| Draw call | 1057 | 992 | **−65** |
| 三角面 | 271 万 | 307 万 | +13% |
| FPS（单次会话三轮中位） | 29.2 | 23.3 | 受热降频影响，见下 |
| FPS（交错 A/B，各两轮） | 26.6 / 29.9 | 22.0 / 30.6 | 区间重叠 |

**结论**：v1.1 比 v1.0 多 13% 三角面（近景草、河道、山体），但少 65 个 draw call（家畜合并 −72，新增内容 +20，其余为合批差异）。无头 Edge 在这台机器上会热降频，同一版本两轮能差 7 FPS，因此两个版本的 FPS 差异落在测量噪声里，不能宣称“更快”或“更慢”；能确证的是 draw call 净减少。

v1.1 真机回归（默认均衡档）：172 个可点对象全部命中、档案卡 7 行、第一人称眼高 1.68 米、雪景正常、控制台 0 报错，QA 记录 57–60 FPS。

**v1.2 生产性空间一轮实测**：`?quality=low&scale=0.75`、480×320、硬件 ANGLE、7 帧中位数，A 基线 712 calls / 3,045,279 tris / 56.5 FPS，B 版 710 calls / 3,049,991 tris / 46.7 FPS（4 s 窗口）。同机位受控隐藏 4 个 `productionMeshes` 前后的净增量是 **+4 draw call / +3,648 三角形**，满足该轮上限 ≤8。

**v1.2 公共核心一轮实测**：同一口径下 A 基线 **761 calls / 3,045,239 tris / 60.1 FPS**（188 对象）→ B 版 **778 calls / 3,052,083 tris / 60.1 FPS**（192 对象）。受控隐藏 5 个 `civicMeshes` 的净增量是 **+5 draw call / +1,180 三角形**（上限 ≤10），三次重复测量恒为 +5；生产性空间回归仍是 +4 / +3,648。绝对总数三次复测 778 / 783 / 799，同版本内可差 20+，来自视锥、家畜与天气相位以及无头环境波动，因此**只报读数、不做绝对差值与 FPS 数值断言**，增量一律以受控开关为准。

三档读数（生产性空间一轮）：流畅 60.3 / 均衡 59.9 / 精致 38.6。

## 九、局限与后续规划

### 9.1 已知局限

- **没有人物**：村里只有牲畜，没有村民，缺少生活气息
- **电线杆与架空线只做到"有"**：当前单文件版里主路沿线有 8 根水泥方杆（横担、绝缘子、拉线）与 23 段下垂导线，贴地形、避让院门与耕地；但杆线不做碰撞，也没有作为独立任务出过完整验收记录（源码来自中断的任务 05，随本轮构建一并进入交付物）
- **生产性空间是静态陈设**：六类物件不参与碰撞、不随时间轴变化，也没有晒粮/喂鸡之类的动画
- **公共核心是静态建筑**：四处新建场所参与第一人称碰撞，但不随时间轴或天气变化，也没有集会/唱戏之类的人群动画
- **建筑是构件拼装**：由盒子与曲面组合，不是高模，贴到墙面近看能看到接缝
- **碰撞是圆形近似**：贴着墙走会有轻微穿插感
- **无音频**：没有风声、鸟叫、脚步
- **仅桌面端**：触屏体验不完整
- **气象是历史数据**：不能接实时天气（要接需要改数据层）
- **河道是高度场下切 + 平面水面**：没有流量、冲刷、汛期水位变化，桥面固定在高程 −0.30 米
